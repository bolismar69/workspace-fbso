# ADR-009: Rate Limiting — Proteção contra Abuso/DoS (Fase 0)

**Status:** ✅ Aceito
**Data:** 2026-06-24
**Substitui:** Nenhum
**Substituído por:** Nenhum

---

## Contexto

O endpoint `POST /calculate` é CPU-intensivo (cálculos financeiros com `shopspring/decimal`, consultas PostgreSQL + Redis por item). Sem proteção, um pico de requisições ou ataque DoS poderia exaurir o pool de conexões PG e degradar todo o ecossistema de faturamento.

DT-11 identificava este risco como **Alta** prioridade.

## Decisão

**Implementar rate limiting sliding window por IP + token JWT, configurável via env vars.**

- `RATE_LIMIT_MAX`: máximo de requisições por janela (default 100)
- `RATE_LIMIT_WINDOW`: janela em segundos (default 60)
- Headers na resposta: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After`
- Bloqueio: HTTP 429 Too Many Requests

Middleware posicionado ANTES do auth no pipeline (bloquear antes de decodificar JWT):
```
recover → requestid → ratelimit → auth → logger → metrics → Handler
```

## Alternativas Consideradas

| Alternativa | Prós | Contras |
|-------------|------|---------|
| **A) Sliding window no middleware** (escolhida) | Preciso, leve, configurável | Estado em memória (não compartilhado entre instâncias) |
| B) API Gateway (Kong) | Centralizado, compartilhado | Dependência externa, latência adicional |
| C) Redis-based rate limiter | Compartilhado entre instâncias | Dependência Redis para funcionamento básico |

## Consequências

- **Positivas:** Proteção imediata contra abuso. Configurável por ambiente (dev: 1000, prod: 100).
- **Negativas:** Rate limit não compartilhado entre réplicas (cada pod tem seu contador). Se escala para 10 pods, limite efetivo = 10 × RATE_LIMIT_MAX.
