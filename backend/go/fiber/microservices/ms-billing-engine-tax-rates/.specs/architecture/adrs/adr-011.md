# ADR-011: CST como Campo Calculado pelo Motor (não Input do Consumidor)

## Contexto

Há ambiguidade sobre se o CST para CBS/IBS deve ser:
- (a) Informado pelo consumidor no request (como ICMS/PIS/COFINS, onde CST/CSOSN depende do regime do emitente)
- (b) Calculado pelo motor com base nas regras fiscais objetivas

## Decisão

**O CST para CBS/IBS é calculado pelo motor**, não informado pelo consumidor. A lógica é:

1. Consultar `iva_dual_rules` → obter alíquotas e percentual de redução
2. Consultar `cst_reforma` → mapear cenário fiscal para o CST oficial
3. Retornar CST no response (campo `TributoItem.CST`)

## Justificativa

- CBS/IBS são tributos "por fora" — o CST reflete a **classificação legal da operação**, não uma opção do emitente
- Diferente de ICMS/PIS/COFINS (onde CST/CSOSN depende do regime do emitente), o CST de CBS/IBS é determinado pela **natureza da operação** (NCM + UF + tipo de produto + flags objetivas)
- A tabela oficial da RFB vincula CST a características objetivas (ex: NCM de cigarro → monofásica → CST 400)
- Consumidores não têm informação suficiente para determinar o CST correto (ex: se o produto é monofásico depende da classificação fiscal, não do regime do emitente)

## Alternativas Consideradas

| Alternativa | Prós | Contras |
|-------------|------|---------|
| **A) CST calculado pelo motor** (escolhida) | Consistente, correto por regras fiscais, consumidor não precisa conhecer classificação | Motor precisa de mais dados (NCM, flags) |
| B) CST informado pelo consumidor | Simples para o motor | Consumidor pode errar CST, divergência fiscal, inconsistente com natureza "por fora" |

## Consequências

- **Positivas:** CST sempre correto conforme regras fiscais. Auditoria centralizada. Consumidores não precisam de conhecimento fiscal profundo.
- **Negativas:** Complexidade adicional no motor. Necessidade de `GetCSTReforma()` no repository.
