# ADR-006: W3C Trace Context — Rastreabilidade Distribuída Ponta a Ponta

**Status:** ✅ Aceito
**Data:** 2026-06-21
**Substitui:** Nenhum
**Substituído por:** Nenhum

---

## Contexto

O `ms-billing-engine-tax-rates` é chamado por múltiplos canais (CRM, e-commerce, ERP, portal B2B). Quando um cálculo de tributos falha ou produz resultados inesperados, é necessário rastrear a requisição desde o canal de origem até a resposta.

Sem tracing distribuído, o diagnóstico depende de correlação manual de logs por timestamp — frágil e lento.

## Decisão

**Implementar W3C Trace Context (`traceparent`/`traceresponse`) como middleware Fiber, com propagação automática de Trace ID entre serviços.**

```
Request → recover → requestid (W3C) → auth (JWT) → ratelimit → logger → metrics → Handler
```

- `traceparent`: propaga o Trace ID original do canal consumidor
- `X-Request-ID`: gerado localmente se ausente (UUID v4), para correlação de logs internos
- `slog` JSON: todo log inclui `trace_id` e `request_id`

## Alternativas Consideradas

| Alternativa | Prós | Contras |
|-------------|------|---------|
| **A) W3C Trace Context** (escolhida) | Padrão aberto, interoperável com Kong/Keycloak | Requer headers dos consumidores |
| B) X-Request-ID apenas | Simples | Sem propagação entre serviços |
| C) OpenTelemetry SDK completo | Telemetria rica | Complexidade adicional, dependência externa |

## Consequências

- **Positivas:** Rastreabilidade ponta a ponta sem depender de plataforma externa. Headers padrão W3C suportados por Kong/Keycloak.
- **Negativas:** `middleware.InitTracing()` (OTEL propagator) não documentado nos diagramas de arquitetura (DT-09).
