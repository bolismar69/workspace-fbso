# ADR-005: DDD com Interface `TaxCalculator` e Injeção de Dependência Manual

**Status:** ✅ Aceito
**Data:** 2026-06-21
**Substitui:** Nenhum
**Substituído por:** Nenhum

---

## Contexto

O motor de cálculo precisa orquestrar múltiplas calculadoras fiscais (IPI, ICMS, PIS/COFINS, CBS, IBS, ISS, FUST, FUNTTEL). Cada calculadora estava em `internal/legacy/` com interfaces específicas, dificultando a composição no pipeline.

## Decisão

**Extrair interface `TaxCalculator` para `internal/domain/` (camada mais interna, zero dependências) e usar injeção de dependência manual no `main.go`.**

```go
// internal/domain/domain.go
type TaxCalculator interface {
    Calculate(ctx context.Context, input models.DocumentoFiscalEntrada) ([]models.ItemDocumentoFiscalSaida, error)
}
```

Calculadoras em `legacy/` e `reforma/` satisfazem a interface via **structural typing** do Go — sem precisar importar o pacote `domain`.

Ordem de inicialização explícita no `main.go`:
```
PostgreSQL → Redis → Repository → Repository com cache → Calculadoras → Engine
```

## Alternativas Consideradas

| Alternativa | Prós | Contras |
|-------------|------|---------|
| **A) DDD + DI manual** (escolhida) | Explícito, testável, zero frameworks | Verboso no main.go |
| B) Framework DI (wire, dig) | Automático | Dependência externa, magia negra, difícil depurar |
| C) Interfaces por calculadora | Flexível | Sem composição uniforme no pipeline |

## Consequências

- **Positivas:** `LegacyAdapter` converte calculadoras legacy → `TaxCalculator`. Pipeline genérico itera sobre `[]TaxCalculator`. Structural typing permite pacotes independentes.
- **Negativas:** `main.go` cresce linearmente com novas calculadoras (~80 linhas de wiring).
