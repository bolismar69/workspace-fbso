## 1. Diagnóstico Inicial

A análise revelou que o cache Redis **já estava implementado** na camada de repository da core-lib
(`taxnexus-individual-core-lib/repository/tax_repository.go`), nos métodos:

- `GetTableConfigs()` — cache de configurações fiscais (chave: `tax_configs:{taxCode}:{YYYY-MM-DD}`)
- `GetTaxRulesForPeriod()` — cache de tabelas progressivas (chave: `tax_rules_list:{taxCode}:{YYYY-MM-DD}`)

Porém, a implementação carecia de **robustez e observabilidade** para uso em produção.

## 3. Estratégia de Cache

| Aspecto | Decisão |
|---------|---------|
| Granularidade | Por data exata (`YYYY-MM-DD`), pois regras fiscais mudam em datas específicas |
| TTL padrão | 12 horas (configurável via `TAX_CACHE_TTL_HOURS`) |
| Chave configs | `tax_configs:{taxCode}:{YYYY-MM-DD}` |
| Chave rules | `tax_rules_list:{taxCode}:{YYYY-MM-DD}` |
| Serialização | JSON (compatível com `decimal.Decimal` via `shopspring/decimal`) |
| Fallback | Redis indisponível → PostgreSQL direto (degradação graciosa) |
| Invalidação | Baseada em TTL — regras fiscais raramente mudam intra-day |

## 4. Observabilidade

Todos os eventos de cache são logados via `slog` com handler JSON:

```json
{"level":"DEBUG","msg":"cache hit","key":"tax_configs:IRPF:2025-12-31","ttl":"12h0m0s"}
{"level":"DEBUG","msg":"cache miss","key":"tax_configs:IRPF:2025-12-31","reason":"not_cached"}
{"level":"DEBUG","msg":"cache set","key":"tax_configs:IRPF:2025-12-31","ttl":"12h0m0s"}
{"level":"WARN","msg":"cache set failed","key":"...","error":"connection refused"}
```
