## 1. Escopo

Expor endpoints `/healthz` (liveness) e `/health` (readiness) para uso por orquestradores de container (Kubernetes, Docker Compose) e balanceadores de carga, permitindo detectar falhas de conectividade com PostgreSQL e Redis sem impactar o tráfego de produção.

---

## 2. Design

### 2.1 Endpoints

| Método | Path | Probe | Descrição |
|--------|------|-------|-----------|
| GET | `/healthz` | Liveness | Verifica se o processo está vivo (sem I/O). HTTP 200 sempre. |
| GET | `/health` | Readiness | Verifica PostgreSQL + Redis. 200 se todos healthy, 503 se algum unhealthy. |
| GET | `/api/v1/health` | Readiness | Idêntico ao `/health`, dentro do grupo API. |

### 2.2 Componentes Verificados

| Componente | Verificação | Timeout |
|-----------|-------------|---------|
| PostgreSQL | `pgxpool.Pool.Ping()` | 2s |
| Redis | `redis.Client.Ping()` (se configurado) | 2s |

Redis é opcional — se `rdb == nil`, o componente não aparece na resposta e não afeta o status.

### 2.3 Response Schema

**Healthy (HTTP 200):**
```json
{
    "status": "healthy",
    "timestamp": "2026-06-20T21:29:11Z",
    "components": {
        "postgresql": {
            "status": "healthy",
            "latency_ms": 2
        },
        "redis": {
            "status": "healthy",
            "latency_ms": 1
        }
    }
}
```

**Unhealthy (HTTP 503):**
```json
{
    "status": "unhealthy",
    "timestamp": "2026-06-20T21:29:11Z",
    "components": {
        "postgresql": {
            "status": "unhealthy",
            "latency_ms": 2001,
            "error": "context deadline exceeded"
        },
        "redis": {
            "status": "healthy",
            "latency_ms": 1
        }
    }
}
```

- Timeout de 2 segundos por verificação via `context.WithTimeout`
- Latência em milissegundos incluída em cada componente
- Mensagem de erro incluída em componentes unhealthy

## 4. Uso com Orquestradores

### Kubernetes
```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 15

readinessProbe:
  httpGet:
    path: /health
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 10
```

### Docker Compose
```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
  interval: 10s
  timeout: 3s
  retries: 3
  start_period: 10s
```

### Dockerfile
```dockerfile
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1
```

## 6. Comportamento em Cenários de Falha

| Cenário | `/healthz` | `/health` | Detalhe |
|---------|-----------|-----------|---------|
| Tudo OK | 200 | 200 | `status: "healthy"` |
| PostgreSQL down | 200 | 503 | `postgresql.status: "unhealthy"` |
| Redis down | 200 | 503 | `redis.status: "unhealthy"` |
| Redis não configurado | 200 | 200 | Redis ausente dos componentes |
| Processo travado | — | — | K8s restart via livenessProbe |
