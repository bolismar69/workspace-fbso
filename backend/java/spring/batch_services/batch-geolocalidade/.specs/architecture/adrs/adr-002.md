# ADR-0002: Padrão Dual Schema (spring_batch + localidade)

## Contexto

O Spring Batch requer tabelas de metadata (`BATCH_JOB_INSTANCE`, `BATCH_STEP_EXECUTION`, etc.) para gerenciar execuções, estados e restartabilidade. Estas tabelas são criadas automaticamente pelo framework.

Paralelamente, o módulo mantém tabelas de negócio (`uf`, `municipio`, `distrito`, etc.) gerenciadas pelo Hibernate/JPA.

A decisão era: colocar tudo no mesmo schema ou separar as tabelas de framework das tabelas de negócio?

## Decisão

**Usar dois schemas PostgreSQL separados:**

- **`spring_batch`**: schema padrão da conexão JDBC (`currentSchema`), onde o Spring Batch cria e gerencia suas tabelas de metadata
- **`localidade`**: schema configurado via `hibernate.default_schema`, onde o Hibernate cria e gerencia as tabelas de negócio

Ambos os schemas são criados idempotentemente no startup via `init-postgres.sql`:
```sql
CREATE SCHEMA IF NOT EXISTS spring_batch;
CREATE SCHEMA IF NOT EXISTS localidade;
```

## Alternativas Consideradas

| Alternativa | Prós | Contras | Motivo da Rejeição |
|---|---|---|---|
| **Schema único** | Simplicidade; menos configuração | Mistura tabelas de framework com negócio; poluição do namespace; dificulta governança | Dificulta separação de permissões e entendimento do modelo |
| **Banco separado** | Isolamento máximo | Overhead operacional (2 conexões, 2 pools); complexidade de deployment | Desnecessário — schemas no mesmo banco oferecem isolamento suficiente |
| **Dual Schema** ✅ | Isolamento limpo; governança clara; permissões separáveis; mesmo pool de conexões | Requer configuração adicional (`default_schema`, `currentSchema`); dois schemas para gerenciar | Escolhida — melhor equilíbrio entre isolamento e simplicidade operacional |

## Consequências

### Positivas
- Separação clara entre metadata de framework e dados de negócio
- Permissões podem ser gerenciadas por schema (ex: usuário batch escreve em `spring_batch`; serviço de API lê de `localidade`)
- Facilita backup/restore seletivo
- Facilita entendimento para novos desenvolvedores
- Mesmo pool de conexões (HikariCP) atende ambos os schemas

### Negativas
- Configuração adicional necessária (`currentSchema` na JDBC URL + `default_schema` no Hibernate)
- Dois schemas para gerenciar em migrations (Flyway/Liquibase no futuro)
- Equipe precisa entender que `currentSchema` ≠ `default_schema`
