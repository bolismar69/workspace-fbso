# ADR-003: Tailwind CSS v4 + Design Tokens CSS Custom Properties

- **Status:** ✅ Aceito
- **Data:** 2026-07-08
- **Decisão por:** Time de Engenharia

---

## Contexto

O projeto precisava de um sistema de estilização que:
- Garantisse consistência visual entre 25+ componentes
- Permitisse tematização futura (dark mode)
- Fosse performático (dead code elimination de CSS)
- Permitesse que os tokens de design fossem compartilhados entre design e código

## Decisão

**Usar Tailwind CSS v4 (CSS-first configuration) com design tokens definidos como CSS Custom Properties com prefixo `--color-solar-*`.**

## Alternativas Consideradas

| Alternativa | Prós | Contras |
|---|---|---|
| **CSS Modules** | Escopo isolado, sem dependência extra | Sem utilitários, mais código CSS manual |
| **Styled Components** | CSS-in-JS dinâmico | Runtime cost, bundle maior, sem dead code elimination |
| **Tailwind v3** | Ecossistema maduro | Config JS em vez de CSS, menos integração com design tokens |
| **Vanilla CSS** | Zero dependências | Sem utility classes, mais propenso a inconsistência |

## Detalhes da Implementação

```css
/* src/app/globals.css */
@import "tailwindcss";

@theme inline {
  --color-solar-primary: #1E5631;
  --color-solar-secondary: #A5C9CA;
  --color-solar-bg: #ffffff;
  --color-solar-bg-alt: #ffffbf;
  /* ... */
}
```

## Consequências

### Positivas
- Design tokens são a fonte da verdade no CSS
- Tailwind v4 gera apenas CSS usado (dead code elimination)
- CSS custom properties permitem troca dinâmica (dark mode futuro)
- Prettier plugin ordena classes automaticamente

### Negativas
- Tailwind v4 é recente (breaking changes em relação ao v3)
- Sem `tailwind.config.ts` — migração de docs/exemplos requer adaptação
- Curva de aprendizado para o time (CSS-first vs JS-first)
