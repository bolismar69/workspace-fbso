# ADR-003: Context API + React Query para Gerenciamento de Estado

- **Status:** Aceito
- **Data:** 2025-07-15
- **Stakeholders:** Time de Engenharia

## Contexto

Definir a estratégia de gerenciamento de estado. Opções:
1. Redux Toolkit
2. Zustand
3. Jotai
4. React Context API + React Query
5. MobX

## Decisão

**React Context API** para estado global síncrono (auth, tema, database connection) + **TanStack React Query** para estado assíncrono (dados do SQLite).

## Justificativa

- **Separação de Concerns**: Context API para estado de UI (tema, auth); React Query para estado de servidor/dados (cache, loading, erro)
- **Simplicidade**: sem dependência adicional de state management library — Context API é built-in
- **React Query**: gerencia cache, invalidação, deduplication, retry, e estados de loading/erro automaticamente
- **Offline-first**: React Query cache persiste dados localmente, perfeito para app sem backend
- **Bundle Size**: Context API não adiciona KB extras; React Query ~12KB gzipped
- **TypeScript**: ambas soluções têm excelente suporte a tipos

## Consequências

### Positivas
- Código mais simples e com menos boilerplate que Redux
- Separação clara: estado de UI vs estado de dados
- React Query abstrai complexidade de cache e loading states
- Sem dependências pesadas de state management

### Negativas
- Context API pode causar re-renders desnecessários se não for bem estruturado
- Sem middleware/devtools como Redux DevTools
- React Query é otimizado para server state — uso para dados locais é menos comum (mas viável)
- Migração para Redux seria necessária se o app crescer muito em complexidade

## Alternativas Consideradas

| Alternativa | Motivo da Rejeição |
|---|---|
| Redux Toolkit | Boilerplate excessivo para o tamanho atual do app; mencionado erroneamente no README |
| Zustand | Bom, mas adiciona dependência sem necessidade (Context API já resolve) |
| Jotai | Foco em estado atômico — overengineering para o escopo atual |
| MobX | Curva de aprendizado com decorators/observables |
