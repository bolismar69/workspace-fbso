# ADR-001: Expo SDK 53 + React Native 0.79 (New Architecture)

- **Status:** Aceito
- **Data:** 2025-07-15
- **Stakeholders:** Time de Engenharia

## Contexto

Na criação do aplicativo Solar Fácil, era necessário escolher entre:
1. React Native CLI (bare workflow) — maior controle, mais complexidade
2. Expo Managed Workflow — desenvolvimento acelerado, menos configuração nativa
3. Expo Bare Workflow — meio termo

## Decisão

**Expo SDK 53 (Managed Workflow) + React Native 0.79 com New Architecture habilitada.**

## Justificativa

- **Produtividade**: Expo managed workflow elimina a necessidade de configurar manualmente módulos nativos, Xcode, Android Studio para builds básicos
- **SDK 53**: versão estável mais recente com suporte a typed routes, Expo Router 5, e New Architecture
- **New Architecture**: `newArchEnabled: true` para usar Fabric renderer e TurboModules — melhor performance de renderização e interop nativa
- **EAS Build**: build pipeline gerenciado que abstrai complexidade de CI/CD nativa
- **OTA Updates**: `expo-updates` permite atualizar o JS bundle sem passar pela revisão das lojas
- **Ecosystem**: acesso a bibliotecas Expo testadas e compatíveis (SQLite, Image Picker, Haptics, etc.)

## Consequências

### Positivas
- Desenvolvimento rápido sem configuração nativa complexa
- Build pipeline gerenciada (EAS Build → App Store / Google Play)
- Atualizações OTA para correções rápidas
- Typed routes com Expo Router

### Negativas
- Limitação a módulos nativos suportados pelo Expo SDK
- Dependência do ecossistema Expo (atualizações de SDK)
- Overhead de build em projetos Expo grandes
- Se um módulo nativo não for suportado, necessário "eject" para bare workflow

## Alternativas Consideradas

| Alternativa | Motivo da Rejeição |
|---|---|
| React Native CLI | Maior complexidade de configuração e manutenção para um time pequeno |
| Expo Bare Workflow | Complexidade adicional sem necessidade imediata de módulos nativos customizados |
| Flutter | Stack diferente, exigiria aprendizado da equipe em Dart |
