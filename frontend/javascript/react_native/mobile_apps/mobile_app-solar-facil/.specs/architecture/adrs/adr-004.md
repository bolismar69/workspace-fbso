# ADR-004: SQLite Offline-First como Fonte Primária de Dados

- **Status:** Aceito
- **Data:** 2025-07-15
- **Stakeholders:** Time de Engenharia

## Contexto

Definir a estratégia de persistência de dados. Opções:
1. Backend remoto (API REST) como fonte de verdade
2. SQLite local com sincronização futura
3. AsyncStorage (key-value) como fonte única
4. Realm ou WatermelonDB

## Decisão

**SQLite local via `expo-sqlite` como fonte primária, com AsyncStorage mantido como legado e plano de migração futura para backend remoto com sincronização.**

## Justificativa

- **Offline-first**: o app funciona completamente sem internet — essencial para usuários em áreas com conectividade limitada
- **SQLite**: banco relacional completo, suporte a queries complexas, constraints, transações
- **Expo SQLite**: integração nativa com Expo managed workflow, sem necessidade de eject
- **Migração gradual**: AsyncStorage existente coexiste enquanto a migração para SQLite avança
- **Futuro**: estrutura relacional facilita sincronização com backend REST/GraphQL quando disponível
- **Performance**: SQLite é mais rápido e flexível que AsyncStorage para dados relacionais

## Consequências

### Positivas
- App 100% funcional offline
- Queries relacionais poderosas (JOIN, WHERE, ORDER BY)
- Constraints de integridade (UNIQUE, CHECK, NOT NULL)
- Transações atômicas (`withExclusiveTransactionAsync`)
- Schema versionado (migrações futuras)

### Negativas
- Complexidade maior que AsyncStorage simples
- Necessidade de estratégia de sincronização quando backend existir
- Schema migrations manuais (não há sistema de migração como Room ou Flyway)
- Dados sensíveis armazenados sem criptografia (risco de segurança)
- Duas fontes de verdade durante período de transição (SQLite + AsyncStorage)

## Alternativas Consideradas

| Alternativa | Motivo da Rejeição |
|---|---|
| Backend Remoto | Não disponível no momento; app precisa funcionar offline |
| AsyncStorage puro | Modelo key-value limitado para dados relacionais como movimentações |
| Realm | Exige eject do Expo; complexidade adicional |
| WatermelonDB | Overhead para o escopo atual; performance extra desnecessária |

## Plano de Migração Futura

Quando um backend estiver disponível:
1. SQLite permanece como cache local
2. React Query gerencia sincronização (queries → API, mutations → API + cache update)
3. Implementar fila de operações offline (pendentes de sync)
4. Estratégia de conflitos: "last write wins" com timestamp
